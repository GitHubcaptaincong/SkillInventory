## 二、管理员登录

采用单管理员方案：
- 使用 Spring Security，不自行设计密码学或会话协议。
- 用户名和密码登录。
- 支持登录、退出、查询当前登录状态。
- 管理员可以管理全部 Skill 和 API Key。
- 不做公开注册、多角色、审批、找回密码、邮件或第三方登录。

密码要求：
- 使用 Spring Security 支持的自适应密码哈希，例如 BCrypt。
- 数据库不保存明文密码。
- 不记录密码、登录请求正文或会话凭证。
- 初始管理员由环境变量提供用户名和初始密码。
- 不设置默认生产密码，不将真实密码提交到 Git。
- 首次没有管理员时才初始化；管理员已存在时不能因重启或修改环境变量而覆盖密码。
- 多实例或并发初始化时不能产生重复管理员。
- 文档说明初始化规则和受控的密码重置/轮换办法。

会话要求：
- 使用服务端会话和 HttpOnly Cookie，不将登录令牌存入 localStorage。
- 会话持久化到现有 MySQL，可使用 Spring Session JDBC；不要引入 Redis。
- 登录成功后更新会话 ID，防止会话固定攻击。
- 退出后服务端会话失效。
- 配置明确的会话有效期。
- Cookie 设置适当的 SameSite、Path 和 HttpOnly。
- HTTPS 部署使用 Secure Cookie；本地 HTTP 调试通过显式配置支持，不要让本地默认启动不可用。
- 使用框架认证和 SecurityContext 持久化机制，避免“登录返回成功但后续请求没有登录状态”。
- 登录失败统一返回用户名或密码错误，不泄露账户是否存在。
- 提供有界的登录失败节流措施，避免无限制暴力尝试；不得以永久锁死管理员为代价。

建议接口：
POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/me
GET  /api/auth/csrf

登录请求使用 application/json。具体响应 DTO 自行设计，并在 API 文档中固定。

## 三、管理接口认证与 CSRF

- /api/admin/** 必须具有有效管理员会话。
- 未登录的 API 请求返回 HTTP 401 JSON，不重定向成 HTML 登录页。
- 管理员登录成功后可使用现有管理能力。
- API Key 不能访问管理接口或替代管理员会话。
- 保留并适配现有 Origin 和 Sec-Fetch-Site 写请求检查。
- Cookie 会话下的写请求启用 Spring Security CSRF 防护，包括登录和退出。
- Vue 正确获取、携带 CSRF Token，登录或退出后按需要更新 Token。
- 不要为方便联调全局关闭 CSRF。
- 精确放行必要认证接口、静态资源和健康检查，不能误放行全部 API。
- CORS 仅允许显式来源；携带凭证时禁止通配符。
- 所有认证、授权和 CSRF 错误使用统一 JSON 错误格式，保留 requestId。

## 四、外部服务使用 API Key 读取 Skill

保护现有三个客户端接口：
GET /api/v1/skills
GET /api/v1/skills/{name}
GET /api/v1/skills/{name}/SKILL.md

统一使用：
X-API-Key: <key>

规则：
- 三个接口均必须提供有效 API Key。
- 管理员浏览器会话不能替代这些接口所需的 API Key。
- API Key 只允许读取全部已发布 Skill，不允许读取草稿或执行任何管理写操作。
- 首版不做逐个 Skill 授权、租户隔离或复杂 scope。
- 不接受 URL/query 参数传递 API Key。
- 未提供、错误、过期或已撤销的 Key，统一返回 401，不泄露 Key 状态细节。
- 有效 Key 读取未发布、已下架或不存在的 Skill 返回 404。
- 认证必须先于业务读取和条件缓存判断；旧 ETag 不能绕过认证。
- 不提供任何未认证的客户端读取旁路。

API Key 存储：
- 使用安全随机数生成足够熵的 Key。
- 可使用固定公开前缀和公开查找标识，便于辨认与检索。
- 数据库仅保存不可逆摘要和必要元数据，不保存完整明文 Key。
- 高熵随机 Key 可以使用 SHA-256 等摘要，不套用人类密码的低熵假设。
- 校验采用合适的恒定时间比较。
- 完整 Key 仅在创建成功响应中返回一次，之后无法从列表或详情再次获取。
- 不将 Key 写入访问日志、异常、埋点、浏览器 URL 或持久化存储。
- 不在前端构建产物中内置任何 API Key。

## 五、API Key 管理

管理员登录后可：
- 创建 Key，填写名称和可选过期时间。
- 查看 Key 列表。
- 撤销 Key。

建议接口：
GET  /api/admin/api-keys
POST /api/admin/api-keys
POST /api/admin/api-keys/{id}/revoke

元数据至少包含：
- id：JSON 字符串。
- name。
- 可展示的前缀/尾号等脱敏标识。
- createdAt。
- expiresAt，可空。
- revokedAt，可空。

规则：
- Key 名称做非空和长度校验。
- 创建时过期时间必须晚于当前时间。
- 状态根据时间和撤销信息计算，避免冗余状态不一致。
- 撤销后立即停止接受该 Key，包括携带旧 ETag 的请求。
- 撤销为幂等操作，不提供恢复。
- 轮换方式是创建新 Key、更新调用方、撤销旧 Key。
- 不做使用统计仪表盘、按请求更新 lastUsedAt 或额外业务缓存。
- Key 列表支持稳定排序和分页。
- 创建和撤销均受会话认证、CSRF 和现有写入来源策略保护。

## 七、缓存与安全适配

- 已认证客户端读取保留 ETag/304。
- 认证失败、授权失败和其他错误均为 Cache-Control: no-store。
- 客户端成功响应使用 Cache-Control: private, no-cache，避免共享缓存混用。
- 适当设置 Vary: X-API-Key，并保留已有必要的 Vary 头。
- Nginx 不缓存认证后的 API 响应，正确透传 X-API-Key。
- 检查代理日志格式，不能记录 API Key、Cookie、密码或完整 Skill 正文。
- 统一错误至少包含 { code, message, requestId }。
- 明确区分 401、403、400、404、409、413、415 和 500，不能全部返回 200。
- 前端路由守卫不是服务端认证，必须测试绕过前端直接调用 API。
- 本次没有要求公网生产级开放。README 说明仍应部署在受控网络，跨不可信网络调用必须使用 HTTPS。

11. 无效 Key 携带旧 ETag 不能获得 304。

13. Key 撤销立即生效，重复撤销符合幂等规则。

16. 登录页、会话失效处理、Key 一次性展示和撤销流程的前端测试。
17. 前端生产构建和真实 MySQL 集成测试。
18. 经 Nginx 的 Docker 冒烟：登录 → 创建并发布 Skill → 创建 Key → 外部读取 → 撤销 Key → 外部读取失败。
19. 普通重启或 down/up 后，管理员和有效 Key 仍可正常使用，Skill 数据仍存在。
